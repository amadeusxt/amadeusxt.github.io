安卓笔记——Jetpack Compose篇

一.初识Jetpack Compose

一.什么是Compose

Jetpack Compose 是 Google 推出的新一代 Android 原生 UI 工具包，用 Kotlin 写界面，不再写 XML

核心区别就一句话：XML 是命令式（告诉系统”怎么改”），Compose 是声明式（告诉系统”长什么样”）

传统 View 体系里，界面是一棵 XML 树，想改界面就得 findViewById 拿到控件再 setText、setVisibility，一步步命令它变

Compose 里，界面是”状态的函数”，状态一变，框架自动帮你把该变的界面重新画一遍，你只需要描述某一时刻界面应该长什么样

对比项 传统 View（XML） Jetpack Compose
界面描述 XML 布局文件 + Java/Kotlin 代码 纯 Kotlin 函数
修改界面 拿到控件对象手动改属性 改状态，框架自动重组
列表性能 ListView/RecyclerView + Adapter LazyColumn，无需 Adapter
代码量 布局与逻辑分离，文件多 一个文件搞定，逻辑与 UI 写一起
复用方式 自定义 View、include 布局 直接调用一个 @Composable 函数
动画 属性动画、手动管理 animate*AsState 一行搞定

补充：Compose 不是”另一个 UI 框架”这么简单，它是把”UI = f(State)”这个函数式思想搬到了安卓上（祖宗之法又被改变了）

三.第一个Compose程序

Compose 不再需要 setContentView(R.layout.xxx)，而是用 setContent 直接塞进去一棵组合树

一般不会把界面直接写在 setContent 里，而是抽成一个独立的 @Composable 函数

四.@Composable注解的规矩

@Composable 是 Compose 的地基，被它标记的函数叫”可组合函数”，它有几个硬性规矩

（1）函数名必须首字母大写（约定俗成，编译器不管，但大家都这么写，因为它在组合树里当”组件”用）

（2）函数不能有返回值，它的作用是”向界面里发射 UI”，不是”返回一个 View 对象”

（3）可组合函数只能在另一个可组合函数里调用，普通函数里调用会直接编译报错

（4）可组合函数要尽量写成”无副作用”的纯函数，给同样的参数就渲染同样的界面，这样框架才敢放心重组

二.Compose的编程思想

一.声明式UI与重组

Compose 的核心循环只有三步：状态变化 → 重新执行可组合函数 → 更新界面，这个过程叫”重组”（Recomposition）

关键点：重组不是把整个界面推倒重来，而是只重新执行”读取了发生变化的状态”的那些可组合函数，其余部分直接跳过

所以 Compose 的性能优化思路和传统 View 完全相反：不是”少改控件”，而是”让重组范围尽量小”

补充：重组是可以被跳过的（skippable），前提是参数类型稳定（Stable）。像 Int、String、函数类型这些默认稳定；而 List、MutableList 这种接口类型被判定为不稳定，会导致跳过失败——这就是为什么官方推荐用 ImmutableList 或者 immutable 注解

二.组合与组合树

Compose 把界面结构叫”组合”（Composition），本质上是一棵树，每个 @Composable 调用就是树上的一个节点

这棵树不是一次性建完的，而是”边执行边建”，所以可组合函数里可以有 if、for、when 这些控制流——这在 XML 里是做不到的

二.Image图片

Image 只负责”画图”，不负责”加载图”，加载网络图得靠 Coil 这类库

IconButton 只有一个图标 工具栏图标按钮

四.TextField输入框

输入框是”受控组件”，值必须由状态提供，不能用传统 View 那种 getText() 的方式去拿

补充：onValueChange 里必须把新值赋回状态，否则你打字框里一个字都不会出现——这是新手第一个坑

四.布局系统

一.Column纵向排列

Column 就是竖着排，等价于 LinearLayout 的 vertical

verticalArrangement 控制”主轴”上的分布，常用值：

取值 效果
Arrangement.Top 顶部开始排（默认）
Arrangement.Center 整体居中
Arrangement.Bottom 底部对齐
Arrangement.SpaceBetween 两端顶死，中间均分
Arrangement.SpaceAround 每个元素两侧间距相等
Arrangement.SpaceEvenly 元素之间与边缘的间距完全相等
Arrangement.spacedBy(8.dp) 固定间距

二.Row横向排列

Row 就是横着排，等价于 LinearLayout 的 horizontal

补充：Column 的主轴是垂直，所以 verticalArrangement 管主轴、horizontalAlignment 管交叉轴；Row 正好反过来。别背，理解”主轴/交叉轴”就够了

三.Box层叠

Box 是层叠布局，子元素会一层层往上摞，等价于 FrameLayout

想让子元素各自对齐不同位置，可以用 Modifier.align 单独指定

四.weight权重

weight 只能在 Row 或 Column 的作用域内使用，用法和 LinearLayout 的 layout_weight 一个意思

补充：weight 的本质是”把剩余空间按比例分”，所以如果某个子元素设了固定宽度，它会先占掉，剩下的再按权重分

五.Modifier修饰符

Modifier 是 Compose 里最重要的一个东西，负责尺寸、内边距、背景、点击、边框、圆角、滚动等等，几乎所有的”属性”都靠它

Modifier 的顺序极其重要，它不是”属性集合”，而是”一层层套上去的包装”

补充：可以把这个理解成”包快递”，padding 是泡沫纸、background 是纸箱，先包泡沫纸再装箱和先装箱再包泡沫纸，最后体积肯定不一样

常用的 Modifier 一览

Modifier 作用
fillMaxSize() / fillMaxWidth() 撑满父容器
size(w, h) / size(48.dp) 固定尺寸
width() / height() 单方向尺寸
padding() 内边距
background() 背景色/背景图
border() 边框
clip() 裁剪形状
clickable {} 点击事件
scrollable() / verticalScroll() 滚动
alpha() 透明度
offset() 偏移
align() Box/Row/Column 内对齐

而且没有 Adapter、没有 ViewHolder，一个 Lambda 就完事了

补充：items 里可以传 key，作用相当于 RecyclerView 的 stable id，能让滑动和增删时状态不串位

三.普通Column的滚动

如果内容不多、不需要懒加载，用 verticalScroll 就够了

补充：verticalScroll 和 LazyColumn 不能嵌套在同一个方向用，会直接崩，报 “Vertically scrollable component was measured with an infinity maximum height constraints”

六.状态管理

一.mutableStateOf与remember

Compose 里”能被观察的变化”必须包在 State 里，最常用的就是 mutableStateOf

但只写 mutableStateOf 不行，因为可组合函数会被反复执行，每次执行都会重新创建一个新状态，值就丢了，所以必须用 remember 记住它

等价的不带委托写法（更容易理解原理）

补充：var count by remember { mutableStateOf(0) } 里的 by 就是 Kotlin 的委托，把读写操作转交给 State 的 value 属性，所以看起来像普通变量，实际上每次读写都触发了状态通知

二.rememberSaveable

remember 只能扛住”重组”，扛不住”配置变更”——比如转屏、切换深色模式，Activity 会重建，remember 里的值就没了

要跨配置变更保留，得用 rememberSaveable，它会把值存进 Bundle

补充：rememberSaveable 只能存能被 Bundle 序列化的类型（基本类型、String、Parcelable 等），存复杂对象得自己写 Saver

三.状态提升

状态提升（State Hoisting）是 Compose 官方反复强调的模式：把状态从子组件里提出来，放到父组件，子组件只负责”显示值 + 上报事件”

好处：子组件变成纯函数，可复用、可预览、可测试；状态集中在父组件，好管理

这就是所谓的”单向数据流”：状态从上往下流，事件从下往上报，绝不让子组件偷偷改父组件的状态

判断一个状态该放哪，就一句话：谁用得多就放谁那儿，但至少得放到”所有使用者的最近公共父级”

四.状态与界面不同步的坑

Compose 的状态更新是异步的，别指望改完状态立刻读到新值

补充：真要在状态变化后做事，用 LaunchedEffect(count) { } 或者 SideEffect，不要在 onClick 里硬读

补充：clickable 默认带水波纹（indication），如果想要无水波纹的点击，用 clickable(interactionSource = remember { MutableInteractionSource() }, indication = null) { }

取主题里的值也很方便

九.副作用与生命周期

可组合函数应该是纯的，但真实项目总要”干点事”：请求网络、注册监听、启动协程。这些”超出渲染本身”的行为叫副作用，Compose 提供了一组 API 来安全地管理它们

API 执行时机 典型用途
LaunchedEffect(key) 首次进入组合时执行，key 变化时重启，离开时取消 请求数据、启动协程
SideEffect 每次成功重组后执行 向非 Compose 代码同步状态
DisposableEffect(key) 进入时执行，离开时走 onDispose 注册/反注册监听器、广播
rememberCoroutineScope 拿到一个绑定当前组合生命周期的协程作用域 在 onClick 里启动协程
produceState 把非 Compose 的数据源转成 State 把回调式 API 包成状态

一.LaunchedEffect

最常用的副作用，进入界面就执行一次（key 传 Unit 或固定值），key 变了就重新执行

补充：LaunchedEffect 的 Lambda 是挂起函数作用域，里面可以直接调 suspend 函数，这就是它比 SideEffect 好用的地方

二.DisposableEffect

需要”配对”的操作就用它，比如注册监听器，退出时必须反注册，不然内存泄漏

三.rememberCoroutineScope

onClick 是普通函数，不能直接调 suspend 函数，这时候就需要一个作用域

补充：scope 的生命周期跟着当前组合走，组件销毁时里面的协程会自动取消，不用担心泄漏

十.与ViewModel结合

一.为什么需要ViewModel

Compose 的 rememberSaveable 只能扛住配置变更，扛不住进程被回收；而且状态和业务逻辑混在 UI 里，一旦界面复杂就变成一锅粥

ViewModel 天生就是干这个的：它在配置变更时存活，生命周期比 Activity 长，正好用来存界面状态 + 跑业务逻辑

二.在Compose里使用

补充：viewModel() 是 lifecycle-viewmodel-compose 提供的函数，会自动从 ViewModelStore 里取实例，没有就创建，转屏后拿到的还是同一个

补充：collectAsState 要在有 Lifecycle 的环境里用，更推荐 collectAsStateWithLifecycle()，它会在界面不可见时自动停止收集，省电

三.UiState模式

稍微正式一点的项目，会把整个界面的状态打包成一个 UiState 数据类，配合密封类表示加载/成功/失败

补充：这里 when 不用写 else，就是因为 UiState 是密封接口，编译器知道所有分支——这正是 Kotlin 篇里密封类的实战用法

二.AnimatedVisibility

控制显示/隐藏的进出场动画，比手写 alpha + translation 省事一万倍

十二.导航Navigation Compose

一.依赖与基本用法

Compose 里没有 Intent 跳转了，页面之间靠 Navigation Compose 管理，本质是一个页面栈

二.传参与返回

补充：导航参数默认都是 String 类型，想要 Int 得在 composable 里声明 arguments = listOf(navArgument(“id”) { type = NavType.IntType })

三.底部导航

底部导航本质就是”多个页面 + 一个切换状态的 NavHost”，Scaffold 提供 bottomBar 插槽

补充：Scaffold 的 innerPadding 必须消费掉，不然内容会被状态栏或底部栏盖住——这是 Compose 里第二个新手大坑

十三.Slot API与组件封装

一.什么是Slot API

Slot（插槽）就是”留个空位让别人往里塞内容”，本质是把 @Composable () -> Unit 当参数传进来

Compose 内置组件几乎全是这个思路：Button 的内容、Scaffold 的 topBar/bottomBar、LazyColumn 的 item，全是插槽

补充：插槽比”传一堆配置参数”灵活得多，因为它能塞任意组件、能拿到作用域里的状态（比如 LazyColumn 的 item 能拿到 index），这是 Compose 组件设计的核心套路

二.Scope与接收者

像 RowScope、ColumnScope 这种叫”作用域”，它让插槽内部能使用 weight、align 这些只有特定布局才有的 Modifier

补充：RowScope.() -> Unit 就是 Kotlin 篇里讲的”带接收者的函数类型”，Compose 把它用到了极致

十四.@Preview预览

Compose 最爽的功能之一：不用装 APK，Android Studio 里直接看界面

常用参数

参数 作用
showBackground 显示白色背景，否则是透明
name 预览面板里显示的名字
widthDp / heightDp 指定预览尺寸
uiMode 切换深色模式预览
locale 切换语言预览
device 指定设备型号
group 分组，预览多的时候好找

补充：想让 Preview 生效，组件必须是”无状态”的或者参数有默认值——这也是状态提升的又一个好处

十六.常见坑与最佳实践

一.几个必踩的坑

（1）在可组合函数里做耗时操作

（2）忘了 remember，状态每次重组都被重置

（3）列表没有 key，增删后状态错位

（4）Modifier 顺序写反，边距背景全乱

（5）在 LazyColumn 里嵌套 LazyColumn 或 verticalScroll，直接崩

（6）用 var 声明普通变量当状态，界面不会更新

二.最佳实践清单

可组合函数保持”无状态”，状态统一提升到上层或 ViewModel

参数用不可变类型，能用 val 就别用 var，能用 List 就别用 MutableList（为了可跳过重组）

一个可组合函数只干一件事，超过 50 行就该拆了

给每个可组合函数配一个 @Preview，多状态都预览一遍

副作用一律走 LaunchedEffect / DisposableEffect，别在函数体里直接开协程

列表一定加 key

主题色统一从 MaterialTheme 取，别在组件里硬编码 Color(0xFF…)

补充：Compose 官方有个原则叫”单向数据流 + 状态提升”，把这两条守住，90% 的架构问题都不会出现

十七.写在最后

从 XML 转到 Compose，最难的不是 API，而是思维方式的转变

XML 时代你是”操作控件的人”，Compose 时代你是”描述界面的人”

刚开始会觉得处处别扭：为什么不能直接改属性？为什么要 remember？为什么改个状态界面就整个重画？

等写过两三个页面就会突然通透了——原来界面真的就只是状态的函数，状态对了，界面自己就对

补充：Compose 和 Kotlin 是绑死的，Kotlin 篇里的高阶函数、Lambda、带接收者的函数类型、密封类、委托、协程，在 Compose 里全都会用到。所以 Kotlin 基础不牢的话，先回去补，不然看 Compose 源码就是看天书
